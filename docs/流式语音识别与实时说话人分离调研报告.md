# 实时流式语音识别 + 实时说话人分离调研报告

> **场景**：macOS + Windows 双端桌面应用，为听障人士提供**实时字幕**
> **硬需求**：① **流式识别**——说话中途就出字（partial results），不等话说完；② **多人对话**按说话人把文字分成不同气泡显示
> **调研方式**：基于官方文档与一手信源（web_search 抓取官方仓库/文档/论文），日期 2025 年
> **配套报告**：[跨平台桌面应用框架选型调研报告](./跨平台桌面应用框架选型调研报告.md)（已选定 Tauri 2.x，本报告聚焦 ASR + 说话人处理本身）

## 0. 结论速览

| 需求 | 现实结论 |
|---|---|
| 本地流式 ASR（离线、Mac+Win） | ✅ **sherpa-onnx 流式 Zipformer** 是唯一"真流式 + 中文双语 + CPU 实时率<1 + 双端可跑"的一站式方案；**Vosk** 真流式但中文弱；whisper.cpp / faster-whisper 是"分块伪流式" |
| 云端流式 ASR | ✅ Azure / 讯飞 / 火山(豆包) / 腾讯 / 阿里 / Google 都支持流式 partial results，中文强；但 **Google 流式不支持 diarization，Azure 实时 diarization 是预览** |
| 实时说话人分离 | ⚠️ **没有"零延迟 + 身份稳定"的完美方案**。真流式 diarization 是研究级（diart / NeMo online / FS-EEND），有延迟且标签会漂移；**现实折中是"切换检测 + 动态注册匹配 + 手动命名"** |
| 推荐组合 | **sherpa-onnx 流式 ASR + VAD + speaker embedding 做在线切换检测/匹配（本地全离线）**，UI 层提供"说话人 A/B/C 气泡 + 手动重命名"；云端可选 讯飞/Azure 做增强 |

## 1. 本地流式 ASR 引擎（可离线，Mac + Windows）

### 1.1 谁真正支持"流式 / 增量（partial results）"？

| 引擎 | 真流式？ | 流式机制 | 中文 | 英文 | 延迟 | CPU/内存 |
|---|---|---|---|---|---|---|
| **sherpa-onnx**（Zipformer Transducer 流式版） | ✅ **真流式** | 内置 streaming 模型，decode chunk 可设（如 320ms/640ms），逐 chunk 出 partial | ⭐⭐⭐⭐⭐（zipformer-bilingual-zh-en / SenseVoice / streaming Paraformer） | ⭐⭐⭐⭐⭐ | 100–300ms 级，RTF 通常 <0.3（CPU 即可实时） | 低（int8 量化后几百 MB~1GB 内存，普通 i5/M1 跑得动） |
| **Vosk** | ✅ **真流式** | Kaldi 原生流式解码，partial results 一等公民 | ⭐⭐（中文模型较弱，词汇有限） | ⭐⭐⭐⭐ | 极低（几十~200ms） | 极低（最轻量） |
| **whisper.cpp** | ❌ 伪流式 | `examples/stream` 用 VAD + 滑动窗口 + 全句重转 | ⭐⭐⭐⭐（Whisper 多语模型） | ⭐⭐⭐⭐⭐ | 较高（要攒够窗口，大模型 CPU 更慢） | 中（ggml 量化，但大模型吃 CPU） |
| **faster-whisper** | ❌ 伪流式 | VAD 切段 + 段级"流式"（RealtimeFasterWhisper / faster-whisper-server 做 partial） | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 中（段级，比 sherpa 流式慢） | 中（CTranslate2 快，但大模型仍要 GPU 才真实时） |
| **groq-whisper** | ⚠️ 云端快速分块 | Groq 是**云端 API**，靠速度（宣称 164× realtime）做近似流式 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 低（但依赖网络+上传） | **非离线**，不能本地跑 |

> **结论**：Mac+Windows 双端离线场景，**"真流式 + 中文强" 只有 sherpa-onnx**；Vosk 真流式但中文不行；whisper 系是"分块伪流式"，延迟与稳定性都不如专用流式模型。

### 1.2 sherpa-onnx 现状（重点）

- **定位**：k2-fsa 团队（Kaldi 作者 Daniel Povey 系）出品，C 库 + 官方 Python / Rust / Node / C# / Flutter / Swift 等 12+ 语言绑定，onnxruntime 推理，**完全离线**，Mac(含 Apple Silicon)/Windows/Linux 全支持。([GitHub](https://github.com/k2-fsa/sherpa-onnx))
- **流式能力**：官方 streaming ASR 示例（microphone / WebSocket server-client）齐全；支持**两遍解码**（streaming 先出字 + offline 重打分提精度）→ `two-pass-speech-recognition-from-microphone.py`。([官方示例](https://github.com/k2-fsa/sherpa-onnx/blob/b74c4dfe/python-api-examples/two-pass-speech-recognition-from-microphone.py))
- **中文多语**：中文流式模型成熟——`streaming-zipformer-bilingual-zh-en`（中英混合）、`streaming-zipformer-ctc`、以及**SenseVoice**（离线、中英日韩等、ASR+情感+事件）、streaming Paraformer。中文 2024 实测对比博客：sherpa-onnx 中文模型（paraformer / zipformer）在清晰普通话上 CER 通常个位数到低双位数。([中文模型实测对比](https://blog.csdn.net/xray4/article/details/154229231) ｜ [pretrained models](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/index.html))
- **配套能力**（对"说话人气泡"直接相关，见第 3 节）：VAD（Silero）、**speaker embedding / speaker identification**（ResNet 说话人嵌入，可动态注册说话人）、**离线 speaker diarization**（pyannote segmentation 模型 + 3D embedding）、音频标签、增强、分离。([Speaker Processing](https://deepwiki.com/k2-fsa/sherpa-onnx/2.4-speaker-processing:-diarization-identification-and-audio-tagging))
- **性能佐证**：官方与第三方 CPU 基准，流式 zipformer 在普通 CPU 上 RTF（实时率）远小于 1（即比实时快数倍），几毫秒~几百毫秒解码延迟。([VoicePing 双端离线转写基准](https://voiceping.net/zh/blog/research-offline-speech-transcription-benchmark/))

### 1.3 成熟的 streaming demo / 库

- **WhisperLive**（collabora）：whisper.cpp + faster-whisper 后端 + VAD 的"准实时"服务器，WebSocket 出 partial；有 diarization 扩展。([GitHub](https://github.com/collabora/WhisperLive/releases))
- **faster-whisper-server**：把 faster-whisper 包成流式 FastAPI 服务（SSE/WebSocket partial）。([GitHub](https://github.com/nirnaim/faster-whisper-server))
- **RealtimeFasterWhisper**：社区实时转写库（VAD+分段）。([GitHub](https://github.com/fless-lab/RealtimeFasterWhisper))
- **WhisperLiveKit**：本地实时 Whisper STT + **实时说话人分离**（Sortformer NeMo 或 diart），带 Web UI，是"本地流式+分离"最接近成品的开源 demo。([GitHub](https://github.com/Ycechung-online/WhisperLiveKit) ｜ [pypi](https://pypi.org/project/whisperlivekit/))
- **sherpa-onnx 官方示例**本身就是最稳的 demo：`streaming-asr` 麦克风 / WebSocket 一键跑。

## 3. 实时说话人分离可行性（关键问题）

### 3.1 "根据音色区分说话人"在实时场景可行吗？

**原理层面可行，工程层面要分清"识别"和"分离"两件事：**

- **音色 → 说话人向量（speaker embedding）**：这是真实做法。把一段语音喂给说话人编码器（ResNet / wavlm / pyannote embedding / NeMo TitaNet），得到一个高维向量；两个人说话向量差异大（余弦相似度低），同一人差异小。**单个短语（1~2 秒）就能算向量**，所以"这一步"本身可以实时。
- **实时可行的部分**：**说话人切换检测（speaker change detection, SCD）**——只要判断"现在这句和上一句是不是同一个人"，用 embedding 余弦阈值即可，几十~几百毫秒延迟，可实时。**这就是给气泡分组的现实基础。**
- **实时困难的部分**：**全量聚类（diarization）**——不知道现场有几个人、没有参考模板时，要把整场录音归成 N 类并给稳定编号。聚类天然需要"看完整段数据"，这是离线任务；强行在线化（滑动窗口聚类）会引入**标签漂移**（同一人中途被改号）和**延迟**（要攒窗口）。

### 3.2 真实的做法：speaker embedding + 聚类

- **经典离线管线（pyannote.audio / NVIDIA NeMo）**：VAD 切语音 → 分段 → 每段提 speaker embedding → **凝聚聚类（agglomerative clustering）** → 输出"谁在什么时间段说话"。([pyannote.audio](https://github.com/pyannote/pyannote-audio) ｜ [NeMo speaker diarization](https://docs.nvidia.com/nemo-framework/user-guide/26.02/nemotoolkit/asr/speaker_diarization/models.html))
- 这类工具 DER（说话人错误率）很低（好数据 <10%），但**需要整段音频**，延迟=录音长度级别，**不能直接用于实时字幕**。

### 3.3 实时 diarization 的延迟与准确性现状：边识别边聚类 vs 先记录后聚类

| 范式 | 代表 | 延迟 | 准确性 | 现状 |
|---|---|---|---|---|
| **边识别边聚类（online/incremental）** | **diart**（基于 pyannote 的流式框架）｜ **NeMo online_diarizer**｜研究级 **StreamingSpeakerDiarization**（overlap-aware）、**FS-EEND** | 秒级~数秒（需攒窗口稳定聚类） | 明显低于离线（聚类窗口短 → 特征不稳），且有标签漂移 | 有可用库，但工程复杂；diart 是其中最"产品可用"的流式 diarization 库 |
| **先记录后聚类（offline）** | pyannote.audio / NeMo / 各家云批量转写 | 录音长度级别 | 最高 | 成熟，但**不是实时字幕**的形态 |
| **切换检测 + 动态匹配（折中）** | sherpa-onnx VAD+embedding 自拼 ｜ alumae/online_speaker_change_detector ｜ WhisperLiveKit(diart) | **百毫秒级** | 分组正确率高（谁跟谁不是同一人），但"这人叫啥"需人工 | **实时字幕最现实的路线** |

**关键论文佐证**：2024 年《Systematic Evaluation of Online Speaker Diarization Systems Regarding their Latency》专门测了多套 online diarization 系统——结论是**在线系统用 DER 换延迟**：延迟越低（几秒内），准确率掉得越多；要接近离线质量得等较长窗口。([arXiv 2407.04293](https://ui.adsabs.harvard.edu/abs/2024arXiv240704293A/abstract))

### 3.4 现实折中：切换检测 + 手动命名 vs 云端 diarization

**方案对比：**

| 方案 | 实时性 | 身份稳定性 | 工程复杂度 | 成本 | 适用 |
|---|---|---|---|---|---|
| **A. 本地：切换检测 + embedding 匹配 + 手动命名**（推荐默认） | ✅ 百毫秒级 | 中（同一人跨长时间可能因模板过期误判，需周期性重匹配） | 低~中（sherpa-onnx 已给 VAD+embedding，自己拼 SCD） | **免费/离线** | 双端离线、隐私优先、看得到说话人的小会 |
| **B. 本地：diart / NeMo online 真流式 diarization** | ⚠️ 秒级 | 低（标签漂移） | 高（Python 环境、模型重） | 免费/离线但吃资源 | 想全自动分组、可接受数秒延迟 |
| **C. 云端：讯飞实时转写(带说话人) / Azure 实时 diarization** | ✅ 秒级 | 高（云端做的好） | 低（SDK 现成） | 按量付费、需联网 | 中文准确率要求高、能联网、愿付费 |
| **D. 云端：批量 diarization（会后补分）** | ❌ 非实时 | 最高 | 低 | 按量付费 | 可作"会后校正"辅助 |

> **推荐**：**默认走 A（本地折中）**——切换检测保证"气泡实时分组"，手动命名让用户（听障者/陪同者）亲自给说话人贴名字，这恰恰是听障字幕软件 UI 上最有价值的交互；若要更稳的全自动分组再加 C 作为增强。**B 目前不建议作为 MVP 主力**（延迟+标签漂移+工程复杂度不成比例）。

### 3.5 支持流式说话人变更检测的开源库

- **sherpa-onnx**（本项目的核心库）：内置 **VAD（Silero）+ speaker embedding（ResNet）+ speaker identification**（可**动态注册说话人**，官方 PR 给了 python 示例）。⚠️ 但**没有开箱即用的"在线说话人变更检测/流式 diarization"组件**——它的 diarization 是**离线**（整段 pyannote 模型）。✅ **好在积木齐全**：VAD 切段 → 每段提 embedding → 与已注册模板算余弦 → 超阈值=同一人 / 低于阈值=新说话人，即可自己实现实时 SCD。([Speaker Identification API](https://k2-fsa.github.io/sherpa/onnx/javascript-api/examples/api_speaker_identification.html) ｜ [动态注册 PR #986](https://github.com/k2-fsa/sherpa-onnx/pull/986/files))
- **alumae/online_speaker_change_detector**（塔尔图大学 Tanel Alumäe）：专门做**在线说话人切换检测**的模型/仓库，正是"实时判断这句话是否换了人"的研究级开源实现。([GitHub](https://relatedrepos.com/gh/alumae/online_speaker_change_detector))
- **diart**（dorucioclea）：基于 pyannote 的**实时说话人分离框架**，流式 block（VAD→分段→embedding→在线聚类），支持重叠语音。([GitHub](https://github.com/dorucioclea/diart) ｜ [pypi](https://pypi.org/project/diart/))
- **NVIDIA NeMo online_diarizer**：官方在线聚类 diarizer，流式处理。([NeMo](https://github.com/tango4j/NeMo) online_diarizer.py)
- **研究级**：`ishine/StreamingSpeakerDiarization`（overlap-aware 低延迟在线）、`Audio-WestlakeU/FS-EEND`（帧级流式端到端）。
- **WhisperLiveKit**：把上述 diart / Sortformer 和流式 ASR 打包成可直接跑的本地 demo（带 Web UI），是最省事的上手参考。([GitHub](https://github.com/Ycechung-online/WhisperLiveKit))

### 3.6 sherpa-onnx 是否内置说话人变更检测？

- **没有内置的"实时说话人变更检测"**。sherpa-onnx 提供的说话人能力：① 离线 speaker diarization（整段音频，pyannote segmentation + 3D embedding）；② speaker identification（对**已知说话人库**做匹配，可动态注册）；③ VAD（语音活动检测）。
- **用它拼实时 SCD 是正道**：VAD 找"一句话"边界 + 该句 embedding 与已注册模板余弦匹配 → 命中=沿用该说话人气泡，未命中=新气泡"说话人 C" → 用户在 UI 上手动命名。这正是第 3.4 节方案 A 的落地方式，**完全离线、双端可跑、百毫秒级**。

## 4. 结论与推荐组合

### 4.1 推荐架构（本地优先 + 云端可切）

```
麦克风/系统音频 loopback（Tauri Rust 层）
        │  16kHz PCM 流
        ▼
sherpa-onnx 流式 ASR（zipformer-bilingual-zh-en / SenseVoice）
   ├─ 每 decode chunk 出 partial text（流式、100~300ms 延迟）
   └─ 句子结束时出 final text
        │
        ▼
说话人管线（并行、本地、折中方案 A）
   ① sherpa-onnx VAD → 切出"一句话/一小段"
   ② sherpa-onnx speaker embedding（ResNet）→ 该段向量
   ③ 与已注册说话人模板算余弦相似度
      · 相似(>阈值) → 归入现有说话人气泡
      · 不相似(≤阈值) → 新说话人气泡（占位名"说话人 C"）
   ④ 用户可在 UI 手动命名/重命名说话人（听障场景关键交互）
        │
        ▼
Tauri 事件 → Web 前端渲染滚动气泡（按说话人着色分组）
```

### 4.2 哪些能做、哪些做不到、限制在哪

**能做 ✅**
- 说话中途出字（真流式 partial results，sherpa-onnx 本地、双端、离线）。
- 中文+英文混合识别，准确率可用（清晰普通话 CER 个位数~低双位数；SenseVoice 更强）。
- 按说话人把文字分成不同气泡：**"切换检测 + embedding 匹配"在百毫秒级实时可行**。
- 用户手动给说话人命名/改色（听障字幕最实用的交互）。
- 全程离线运行（无网络、隐私好、无持续费用）。

**做不到 / 打折 ⚠️**
- **实时全自动 diarization + 身份永不漂移**：做不到。流式聚类有秒级延迟 + 标签可能中途改号；要身份稳定必须走云端（讯飞/Azure）或会后离线校正。
- **重叠说话**：两人同时说话时 ASR 与 diarization 都会退化（有 overlap-aware 研究模型，但准确率仍不如单人）；会议多说话人+重叠是最大短板。
- **"他到底是谁"**：音色只能分组不能认人，**必须靠用户命名/注册模板**才有人名；跨天重开会话身份不延续（除非持久化模板库）。
- **远场/嘈杂/回声**：麦克风远、会议 room tone、回声（如果开扬声器放会议声音）都会同时拖低 ASR 与 SCD 精度。
- **纯本地 CPU 承载**：流式 ASR + embedding 同机运行，普通 PC 没问题，但别在跑 ASR 的机器上再叠加重型在线 diarization（diart/NeMo）——会抢资源。

### 4.3 分阶段落地建议

1. **MVP（推荐先做）**：sherpa-onnx 流式 ASR（zipformer-bilingual-zh-en）+ VAD + speaker embedding 自拼 SCD，UI 出"说话人 A/B/C 气泡 + 手动命名"。
2. **增强（可选）**：接入 WhisperLiveKit 或 diart 试试自动分组体验，评估标签漂移是否可接受；加"重匹配/回填"机制（每 N 分钟用整段重聚类校正一次标签）。
3. **付费云端（可选）**：需要最强中文 + 稳定身份时，切讯飞实时转写（带说话人分离）或 Azure 实时 diarization（预览）；本地/云端抽象成同一接口。
